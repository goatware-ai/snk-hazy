## 1. Every prompt requirement has its own row

- The Rubric requirement mapping check walks every material requirement in the prompt and
  demands a dedicated criterion. After ANY restructure, split or weight cut, re-walk the prompt's
  deliverable sentences one at a time and name the row covering each; a weight cut is a coverage
  change and has cost two submissions (2026-08-25 and 08-31). Ask what a deliverable
  could omit while still passing every criterion.
- An aggregate does not map a breakout ("66 units uncovered" does not cover "by item, by branch
  and by month with a reason"): write the breakout as a presence claim over rows keyed on the
  workbook's own header words (WHY IT IS SHORT, WHO, BY WHEN), never as a count. A negative's
  carve-out is not a mapping ("mentions the content in passing"). A clause added to the prompt
  for metadata reasons still needs its own row. Budget one parent PRESENCE row per deliverable
  section the prompt requires; the review wants it even when detail rows score the section.
- Read every prompt sentence for a deliverable the rubric only IMPLIES: "every line that billed
  wrong and what it should have billed" mapped to nothing when every EXC row pinned a total or a
  selected example, and omitting all 332 lines retained 100% (the completeness check cannot see it, the tag was fat).
  The REGISTER row: "+5, worked as N rows, each carrying <the row's columns>, the N a formula over
  the list rather than a keyed figure", plus a +1 per-row formula clause beneath it, so the
  line-level cluster costs 6 of 39; cause rows get the operand-free gated clause so totals
  demonstrably derive from it.
- R13's coverage block counts only COMPLETENESS_RE rows ("exactly once", each/all within 90 chars
  of a number): phrase coverage "on each of the 26 catalog rows" mid-sentence (a leading "Each"
  trips W11) and the count-cell row "counts all 26 catalog rows by a formula".
- A prompt demand of "every/all items" needs an explicit completeness criterion pinning the exact
  qualifying count with the exclusion arithmetic inline ("47 SKUs: 56 rows, dup counted once,
  minus 6 press, minus 2 frozen") plus carve-outs for legitimately excluded rows. Symmetric events
  in the inputs (two supersessions, two discontinued items) get mirrored criteria.
- Every prompt-named deliverable basename appears verbatim in a positive criterion (R83, the
  platform's filename format coverage check); the +1 file row is never droppable coverage. Because
  the review rejects a name-only row ("grades location/path rather than content"), carry the
  basename inside a content claim: "The memo, <basename>, is addressed to <addressee> and covers
  <period>". R102 errors when the prompt names an addressee no positive grades; R101 when a
  labelled block on the golden's front page is scored by no criterion; R97 when a month-split
  table the golden carries is scored by no row that NAMES a month.
- A reviewer maps every prompt clause and every golden action row to a criterion: a deadline on
  every claim, a reason on each under-billed invoice, correctness of all 122 rated amounts (pin
  it with the $-marked column total), an item under every attribute with an exception, each
  action row. A reviewer coverage list has to fit the 39 cap by displacing +1 rows: decide the
  single points first, spend them on the reviewer's rows, and LOG every dropped row. Buy a row at
  the cap by dropping criteria whose substance another FORCES (a variance reading zero forces the
  base-period rule; pinned 163 and 375 force 538).
- The rubric must fail the golden's own defects: pin the facts a reviewer verifies (identifiers,
  the document date, the signature line, each policy class closed) so a wrong golden loses
  points under its own rubric ("the rubric clearly did not catch the issues", a task).

## 2. Cluster share (the completeness check) and scope (R73/R74)

- The full credit completeness check tests EACH explicitly named prompt deliverable: if omitting
  that requirement's whole cluster retains ~90% of positive weight, FAIL; the bar is
  approximate and its own addition drifts by one, so every tag needs over 12.5% plus a one-point
  cushion. Mirrored negatives buy no cover
  (they fire on commission, not omission) and an omission-firing negative flakes.
- Clusters come from the PROMPT, not the tags: the recommendation and the action plan are tested
  SEPARATELY (each needs its own rows; a +5 figure read-through on the front page counts for
  neither); an exhaustive formula carry ("all 792 tickets") is its own cluster for N >= 100; an
  AND-list ("who orders when, whose truck it rides, and the wait") is one cluster per limb scored
  on DIRECT rows only, with a strict liveness row refused as coverage for its own noun. Under that
  split 12.5% per noun is unreachable at +39, so the completeness check floors at the stated 7% plus drift with
  strict rows crediting LIVE only; design rule: every prompt noun, each limb included, gets 3-5
  direct points BEFORE the first submission, or the prompt is written with fewer limbs. Count
  the named deliverable phrases before building: at seven the rubric has zero slack, at eight it
  cannot pass; write prompts with at most six named outputs.
- A strict read-through credits a requirement only when its anchored figure IS that
  requirement's own output (the far minimum for POLICY, the far stop cost for COST), never a
  downstream front-page total; pick the two strict anchors from two different requirements'
  outputs on working sheets. With R24 pinning positive at 39 and the strict pair taking 10, the
  remaining 74% affords about five clusters: fold requirements (SHORT rode into SOURCE) rather
  than add rows.
- A cluster may sit under the bar only when omission is not separable (skipping it corrupts other
  rows' pinned figures and trips two -4s, the contract carve-out).
- R73: a prompt demanding live formulas needs the gated non-strict tier over 15% of positive,
  because "two isolated outputs ... a selectively hard-coded workbook still earns all 39/39".
- R74, the SCOPE axis: a liveness row that buys credit for a container rather than its contents
  (two cell-level rows at 25.6% still let every downstream total be hard-coded; one point for 28
  supplier-call rows with no supplier and no call). Test every criterion by asking what a
  deliverable satisfying its words while omitting the substance looks like; hang an inseparable
  formula clause on the totals rows already present (39/39 retained became 30/39). A criterion
  cannot ask the judge to edit and re-check the workbook, and formulas across every row is W16;
  put the formula demand on one named row and let the sweep ask only for presence.
- Splitting a carry row halves the carry (R85): re-fund the formula rows and the count row to +2
  by cutting base-count rows and dropping a +1 row, never by raising the total.

## 3. Subsumption and overlap

- A universal DERIVATION positive subsumes the rows scoring named instances of it (R57): narrow
  the universal to the aggregate total plus the general method and keep the named rows as spot
  checks (weight-neutral); presence over every row ("carries an action") is coverage and safe,
  correctness over every row is subsumption.
- Subsumption needs no shared figure (R86): a field-list row ("each claim carrying the pro, ...,
  and the reason code") subsumes a per-item presence row on one of those fields; the repair is a
  DISTINCT property of the attribute (reconciliation of the schedule's code counts to the grouped
  summary), never a bundle. One total, one criterion (R95/R12): the mechanics sibling drops the
  total token entirely.
- Two rows at different figures for one named quantity are a contradiction (R60,
  [[rubric-anchoring-and-landing]]); a liveness anchor another row scores is R45/R47
  ([[rubric-liveness-criteria]]).
- Merge derivable pairs into a two-figure row (50 + 66 + 6 = 122 as one row of two figures), never
  the four-figure bundle a review suggests (R27).

## 4. Owners, dates and named people (R81 / R100)

Owner and date rows are bounded on both sides:

- R81 (2026-09-02, Rubric Quality Review): a positive never fixes an action's
  owner to a named PERSON, even when the name sits in the prompt or inputs; a valid alternative
  assignment must not lose points. A golden should not invent an owner either (name one the inputs
  carry). One owner per action row when a row names the owner; a two-name row flaked 1/3.
- R100 (2026-09-09, adjudication): when the prompt never asks who owns an action
  or by when, a row must not score an owner or a date AT ALL ("so that credit turns on the
  substance of the change alone"); put the ask in the prompt if the task needs it.
- Only when the prompt does ask for owners and dates does the reviewer round-3 wording apply: a
  bare "an owner" was ruled "unspecified, no acceptance criteria", so the row writes the test
  itself, "with a named person as owner and a calendar date", still never naming the person.
- Basis-dependent pins: a figure that falls out of an assumption a sibling criterion leaves open
  (176 pieces on a three-month horizon the coverage row lets the solver change) is tagged with the
  assumption, and the dependent rows say "on the three month horizon that is X".
- A rules-only row carries the cited section's own exceptions ("unless / where ... does not /
  also": seasonal-equivalent ranking, the reserve-rack carve-out); the reviewer reads each row
  against the golden's correct placements.

## 5. The reviewer's input window (28 observed, 25 prescribed)

- The Rubric Quality Review reads an input xlsx through a window of about 28 data rows (header at
  row 3, rows 4-31 on one task): a worked example anchored on tag T574 at row 77 was called
  "non-existent" and a count of 75 "could not be verified from the 28-tag cage count". The house
  rule keeps examples inside the first 25 data rows as a cushion of three. A count over the whole
  file, or an example past the window, reads as golden-only (one round 4: six hazmat, 30
  no-pick, FT1319 at row 169); when the window holds no instance of a rule, the row is the rule
  and its section alone, and the oracle verifies it against the deliverable. Never pin a count of
  input rows unless the deliverable reports it in a labelled cell. Procedure parameters, the
  email's budget and the row count survive as figures. The oracle judge reads whole sheets but
  not the tails of long prose cells (R103, [[rubric-anchoring-and-landing]]).
- Record ids past the window are the same miss, now coded (R107, RUBQ-GROUND, 2026-09-11): the
  one round pinned transaction and adjustment ids sitting at rows 122 to 407 of the logs
  and drew a [critical] ungrounded_verification on eleven rows; the review named rows 2 to 30 as
  what it saw and read the cycle count's in-window rows as "no variance data". A deep
  record is scored as the deliverable's property (cites the records by id, what the finding
  states) with no id, quantity, date or status token; a docx or prompt fact is always in view.
- The citation FRAME fails the window as surely as the id (R110, 2026-09-11, round 3): "cites by
  transaction id the outbound pick transactions" for a SKU whose records sit past row 28 drew the
  same six [critical] findings as the id rows had. Rows the review passes state the memo's decision
  and reason in the memo's words; write an explanation row as what the explanation attributes or
  states, never as what a log shows or what the memo cites, and keep log names out of it.
- A plain "by X and Y" ask needs a row cueing both dimensions (R115, PRE-COVER, 2026-09-11): the
